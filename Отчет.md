# Отчёт по домашнему заданию

## 1. Доменная область приложения

Приложение представляет собой небольшой и простой трекер задач. Пользователь может создавать задачи, просматривать список задач и отдельную задачу, изменять название, описание и статус выполнения, а также удалять задачи.

## 2. Стек реализации

### Frontend

- React
- TypeScript
- Vite сборка и локальный dev server
- nginx раздача статики в docker и reverse proxy
- HTTP/REST для взаимодействия с backend

### Backend

- Python 3.11
- FastAPI
- SQLAlchemy 2
- Psycopg 3
- Uvicorn
- Alembic - миграции БД

### Хранение данных

- PostgreSQL 17

### Запуск и окружение

- Docker
- Docker Compose
- Nginx для раздачи production-сборки frontend

## 3. Основные сущности доменной области

В приложении используется одна основная сущность `Task` - задача.

Поля сущности:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | integer | Уникальный идентификатор задачи |
| `title` | string | Название задачи |
| `description` | text | Описание задачи |
| `is_completed` | boolean | Признак выполнения задачи |
| `created_at` | datetime | Дата и время создания |
| `updated_at` | datetime | Дата и время последнего изменения |

Для сущности реализован полный набор CRUD-операций:

- Create - `POST /api/tasks`
- Read - `GET /api/tasks`, `GET /api/tasks/{id}`
- Update - `PUT /api/tasks/{id}`
- Delete - `DELETE /api/tasks/{id}`

## 4. Соответствие методологии 12 факторов

### I. Кодовая база

Frontend и backend находятся в одном репозитории и представляют одну кодовую базу приложения.
Различные окружения (разные настройки в .env) используют одну и ту же кодовую базу.

### II. Зависимости

Все зависимости объявлены явно:

- backend - в `backend/requirements.txt`;
- frontend - в `frontend/package.json`.

У них указаны конкретные версии.

При запуске через Docker все компоненты работают в изолированных контейнерах и не зависят от глобально установленных библиотек на машине запуска. 

### III. Конфигурация

Конфигурация вынесена из исходного кода в переменные окружения.

Docker Compose читает значения из .env, backend получает их через pydantic-settings.

Локально frontend использует VITE_API_URL. В Docker переменная не задаётся, поэтому запросы идут на относительный путь /api текущего хоста. Nginx принимает их и проксирует на backend:8000.

Изменение окружения не требует изменения исходного кода.

### IV. Сторонние сервисы

PostgreSQL рассматривается backend-приложением как внешний ресурс. Backend знает о базе только через строку подключения `DATABASE_URL`.

Поэтому локальную PostgreSQL из Docker Compose можно заменить, например, на облачную PostgreSQL без изменения кода приложения - достаточно изменить переменную окружения.

### V. Сборка, релиз, запуск

Стадии логически разделены.

Build. На этапе сборки из исходного кода создаются готовые Docker-образы. Для frontend Vite выполняет `npm run build` и формирует статические файлы, которые затем помещаются в образ nginx. Для backend в образ устанавливаются Python-зависимости и копируется исходный код приложения.

Release. Готовый образ объединяется с конфигурацией конкретного окружения. Параметры подключения к PostgreSQL, порты и другие настройки передаются через переменные окружения и .env.

Run. На этапе запуска используются уже готовые образы: nginx раздаёт собранный frontend и проксирует API-запросы, а Uvicorn запускает FastAPI backend. Сборка исходного кода на этапе запуска не выполняется.

### VI. Процессы

Backend не хранит пользовательские или доменные данные в памяти процесса. Все постоянные данные задач находятся в PostgreSQL.

Если backend-процесс будет перезапущен или заменён другим экземпляром, данные не потеряются. Это позволяет в дальнейшем запускать несколько экземпляров backend за балансировщиком.

Frontend также не хранит постоянные данные. React-приложение сохраняет только временное состояние интерфейса в браузере пользователя: открытые модальные окна, введённый текст формы, загруженный список задач. После обновления страницы временное UI-состояние теряется, а данные задач повторно загружаются из backend.

Контейнер frontend с nginx является stateless: он только раздаёт статические файлы приложения и проксирует API-запросы. Поэтому его также можно перезапускать или масштабировать без потери данных.

### VII. Привязка портов

Backend самостоятельно поднимает HTTP-сервер Uvicorn и слушает порт `8000`.

Frontend отдаётся Nginx через порт `80` внутри контейнера и публикуется Docker Compose на порту `8080` хостовой машины.

Оба компонента доступны как самостоятельные сетевые сервисы через явно объявленные порты.

### VIII. Параллелизм

Backend является stateless и не привязан к конкретному локальному состоянию процесса. Поэтому количество экземпляров backend можно увеличивать горизонтально. Состояние при этом остаётся в общей PostgreSQL.

Frontend также можно масштабировать горизонтально. Контейнер с nginx не хранит пользовательское состояние и только раздаёт статические файлы React-приложения и проксирует API-запросы. Поэтому можно запускать несколько экземпляров frontend-контейнера за балансировщиком.
Состояние самого React-интерфейса хранится в браузере конкретного пользователя и не влияет на возможность масштабирования серверной части frontend.

### IX. Утилизируемость
Backend быстро запускается и не хранит доменные данные в памяти. Для каждого запроса используется отдельная AsyncSession, которая закрывается после обработки.

Frontend-контейнер с nginx сразу раздаёт готовую React-сборку и не хранит пользовательские данные.

Frontend и backend можно безопасно перезапускать без потери данных, так как постоянное состояние хранится в PostgreSQL, а данные БД - в Docker volume.

### X. Паритет разработки и продакшена

Основной стек одинаков в development и production: React, FastAPI и PostgreSQL используются в обоих окружениях.

Backend запускается одинаково, меняются только значения конфигурации.

Для frontend есть одно отличие: локально используется Vite dev server, а в Docker - nginx, который раздаёт production-сборку и проксирует /api.

Различие ограничено способом раздачи frontend; API, backend и база данных остаются теми же.

### XI. Логгирование

Приложение не пишет собственные лог-файлы на диск. Uvicorn выводит HTTP- и application-логи в stdout/stderr.

Frontend-контейнер с nginx также не хранит логи в файлах приложения. Nginx выводит access- и error-логи в стандартные потоки контейнера, а клиентские ошибки React доступны в консоли браузера.

Docker собирает стандартные потоки контейнеров, поэтому логи доступны через `docker compose logs`.

### XII. Административные задачи

Для административных задач БД используется Alembic.
Изменения схемы БД оформляются как отдельные миграции и запускаются разовой командой:

```bash
alembic upgrade head
```

Миграции используют ту же конфигурацию подключения к PostgreSQL, что и приложение, и выполняются отдельно от основного backend-процесса.
