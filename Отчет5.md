
# 1. Выбранные показатели и целевые значения

| SLI                                                  | Источник данных                                                                           | SLO (внутренняя цель) | SLA (обязательство) |
|------------------------------------------------------|-------------------------------------------------------------------------------------------|-----------------------|---------------------|
| Доступность frontend и backend, отдельно для каждого | `probe_success` от Blackbox Exporter                                                      | >= 99,9%              | >= 99%              |
| Доля HTTP-запросов без ошибок 5xx                    | `http_requests_total` от FastAPI                                                          | >= 99,9%              | >= 99%              |
| Доля HTTP-запросов длительностью не более 500 мс     | `http_request_duration_seconds_bucket` и `http_request_duration_seconds_count` от FastAPI | >= 95%                | >= 90%              |
| Успешность создания задач                            | `tasks_created_total` и `http_requests_total`                                             | >= 99,9%              | >= 99%              |
| Успешность удаления задач                            | `tasks_deleted_total` и `http_requests_total`                                             | >= 99,9%              | >= 99%              |

SLA доступности приложения: 99% за календарный месяц.

Для демонстрации SLI рассчитываются за последние 5 минут. Целевые значения SLO и SLA заданы для календарного месяца.

# 2. Формулы расчёта SLI

## 2.1. Доступность frontend и backend 

`SLI_availability = 100 * (число успешных проверок / число всех выполненных проверок)`.

```promql
100 * avg_over_time(probe_success{job="blackbox"}[5m])
```

SLO: `vector(99.9)`; SLA: `vector(99)`.

## 2.2. Доля HTTP-запросов без 5xx 

`SLI_http = 100 * (все запросы − запросы с 5xx) / все запросы`.

```promql
100 * (
  1 -
  (sum(increase(http_requests_total{status="5xx"}[5m])) or vector(0))
  /
  sum(increase(http_requests_total[5m]))
)
```

SLO: `vector(99.9)`; SLA: `vector(99)`.

## 2.3. Доля быстрых HTTP-запросов 

`SLI_latency = 100 * (число запросов длительностью <= 0,5 с / число всех запросов)`.

```promql
100 *
sum(increase(http_request_duration_seconds_bucket{le="0.5"}[5m]))
/
sum(increase(http_request_duration_seconds_count[5m]))
```

SLO: `vector(95)`; SLA: `vector(90)`.

## 2.4. Успешность создания задач 

`SLI_create = 100 * (число успешно созданных задач / число попыток создания задач)`.

```promql
100 *
sum(increase(tasks_created_total[5m]))
/
sum(increase(http_requests_total{
  method="POST",
  handler="/api/tasks"
}[5m]))
```

SLO: `vector(99.9)`; SLA: `vector(99)`.

## 2.5. Успешность удаления задач 

`SLI_delete = 100 * (число успешно удалённых задач / число попыток удаления задач)`.

```promql
100 *
sum(increase(tasks_deleted_total[5m]))
/
sum(increase(http_requests_total{
  method="DELETE",
  handler="/api/tasks/{task_id}"
}[5m]))
```

SLO: `vector(99.9)`; SLA: `vector(99)`.

В показателях создания и удаления задач количество успешных операций определяется по бизнес-счётчикам, а общее количество попыток — по HTTP-запросам соответствующих маршрутов. Предполагается, что одна успешная операция соответствует одному HTTP-запросу. В число попыток включаются также запросы, завершившиеся ошибками.

При отсутствии запросов за выбранный период request-based SLI не рассчитывается.

# 3. SLA и бюджет ошибок

Общее SLA Task Tracker — 99% доступности за календарный месяц. Доступность frontend и backend оценивается по отдельным проверкам; выполнение общего SLA требует соблюдения обоих порогов.

Дополнительно установлены SLA для успешности и длительности HTTP-запросов, а также для пользовательских операций создания и удаления задач.

Для 30-дневного месяца бюджет ошибок составляет:

| Показатель | Бюджет по SLO | Бюджет по SLA |
|---|---|---|
| Доступность frontend и backend (для каждого) | 43 мин 12 с недоступности | 7 ч 12 мин недоступности |
| HTTP-запросы без 5xx | <= 0,1% запросов с 5xx | <= 1% запросов с 5xx |
| HTTP-запросы <= 500 мс | <= 5% медленных запросов | <= 10% медленных запросов |
| Создание задач | <= 0,1% неуспешных попыток | <= 1% неуспешных попыток |
| Удаление задач | <= 0,1% неуспешных попыток | <= 1% неуспешных попыток |

Бюджет недоступности рассчитывается по формуле:

`Бюджет = длительность периода * (1 − целевая доступность)`

Для request-based показателей бюджет определяется допустимой долей неуспешных или медленных запросов.

# 4. Изменения приложения и инфраструктуры

Для мониторинга доступности приложения установлен Blackbox Exporter с помощью Helm. Настроены HTTP-проверки frontend (`/`) и backend (`/api/tasks`) с периодичностью 15 секунд. Проверка backend также затрагивает PostgreSQL, поскольку получение списка задач требует обращения к базе данных.

В конфигурацию vmagent добавлен `scrape_config` для пробера. Результаты проверок сохраняются в Victoria Metrics.

Для оценки успешности и длительности HTTP-запросов используются метрики FastAPI, реализованные в предыдущем домашнем задании.

Для оценки доступности пользовательских операций используются существующие бизнес-метрики `tasks_created_total` и `tasks_deleted_total` совместно с HTTP-счётчиками запросов на создание и удаление задач.

Графики SLI строятся в Victoria Metrics (VMUI) с пятиминутным окном расчёта. Для сравнения отображаются пороги SLO и SLA.

## 5. Демонстрация

На скринкасте показаны создание и удаление задач, успешные и ошибочные HTTP-запросы, временная остановка backend (посредством остановки базы данных) и восстановление его работы.

В VMUI продемонстрировано изменение метрик и SLI относительно порогов SLO и SLA. Для расчёта используется окно 5 минут.
