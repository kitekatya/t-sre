# Отчёт по домашнему заданию

## 1. Какие абстракции Kubernetes использованы

Для развёртывания приложения в minikube использованы следующие абстракции Kubernetes.

### Deployment

`Deployment` используется для постоянно работающих компонентов приложения:

- backend;
- frontend;
- PostgreSQL.


Для backend и frontend `Deployment` позволяет задавать количество реплик и масштабировать приложение командой:

```bash
kubectl scale deployment backend --replicas=3
```

Kubernetes следит за указанным количеством Pod'ов и при необходимости пересоздаёт их.

PostgreSQL запускается в одном экземпляре. Простое увеличение `replicas` для базы данных не настраивает репликацию данных: несколько Pod'ов PostgreSQL не синхронизируют состояние. Для такой схемы требуется отдельная настройка репликации или использование StatefulSet/оператора PostgreSQL. 

### Service

`Service` используется для сетевого взаимодействия между компонентами приложения.

Созданы следующие сервисы:
- `backend` - предоставляет доступ к backend внутри кластера на порту `8000`;
- `db` - предоставляет доступ к PostgreSQL на порту `5432`;
- `frontend` - предоставляет доступ к nginx/frontend через браузер.

Backend обращается к PostgreSQL по имени сервиса `db`, а nginx обращается к backend по имени сервиса `backend`.

Для `frontend` используется `Service` типа `NodePort`, чтобы приложение можно было открыть с хостовой машины через minikube.

### PersistentVolumeClaim

Для PostgreSQL используется `PersistentVolumeClaim`.
Он предоставляет постоянное хранилище для данных базы данных, чтобы данные не зависели от жизненного цикла конкретного Pod'а PostgreSQL.

### Secret

`Secret` используется для хранения чувствительной конфигурации приложения:
- имени базы данных;
- пользователя PostgreSQL;
- пароля PostgreSQL;
- строки подключения `DATABASE_URL`.
Значения из `Secret` передаются в контейнеры через переменные окружения.

### ConfigMap

`ConfigMap` используется для несекретной конфигурации `backend`.
В текущей версии через него передаётся значение `CORS_ORIGINS`. В Kubernetes-сценарии эта настройка не является критичной, так как браузер обращается к API через nginx на том же origin, а nginx уже проксирует запросы на backend внутри кластера.

### Job

Для применения миграций базы данных используется `Job`.
`Job` запускает образ `backend` с командой:

```bash
alembic upgrade head
```

После успешного применения миграций `Job` завершается.
Перед выполнением миграции используется `initContainer`, который с помощью `pg_isready` ожидает готовности PostgreSQL. Это позволяет применять все манифесты одной командой, не завися от порядка запуска Pod'ов.


## 2. Как сервисы приложения взаимодействуют между собой

Приложение состоит из frontend, backend и PostgreSQL.

Frontend отвечает за пользовательский интерфейс и работает через nginx. Backend обрабатывает API-запросы и взаимодействует с базой данных PostgreSQL. Для связи между компонентами используются Kubernetes `Service`, поэтому сервисы обращаются друг к другу по стабильным DNS-именам, а не напрямую по IP-адресам Pod'ов.

Перед началом работы приложения схема базы данных приводится к актуальному состоянию отдельным Kubernetes `Job`. Перед запуском Alembic `initContainer` ожидает готовности PostgreSQL через сервис `db`, после чего выполняется команда `alembic upgrade head`.

Схема взаимодействия:

```text
Browser
  |
  v
frontend Service
  |
  v
frontend Pod / nginx
  |
  |
  v
backend Service
  |
  v
backend Pod(s)
  |
  v
db Service
  |
  v
PostgreSQL Pod
```
и
```text
migrate Job
  |
  v
db Service
  |
  v
PostgreSQL Pod
```
